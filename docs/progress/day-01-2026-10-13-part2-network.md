## 1. Objective

Give every server a **fixed, predictable address** on the internal lab network and make gw01 the only way in and out:

- gw01 keeps one internet-facing adapter (DHCP from VMware NAT) and gets a static internal address.
- app01 and stor01 get static internal addresses only, with gw01 as their default gateway.

Fixed addresses are required for everything that follows: firewall rules, NFS exports, monitoring targets, VPN routes and the Ansible inventory all refer to these IPs.

## 2. Network design

| Network | VMware switch | Subnet | Purpose |
|---|---|---|---|
| External | VMnet8 (NAT) | 192.168.229.0/24 (DHCP) | Internet access, **gw01 only** |
| Internal lab | VMnet2 (isolated custom switch) | 192.168.60.0/24 (static) | Server-to-server traffic |

| Host | External (ens33) | Internal (ens34) | Default gateway |
|---|---|---|---|
| gw01 | DHCP, 192.168.229.155 | 192.168.60.1/24 | VMware NAT (via ens33) |
| app01 | disconnected | 192.168.60.10/24 | 192.168.60.1 (gw01) |
| stor01 | disconnected | 192.168.60.20/24 | 192.168.60.1 (gw01) |

**Design note:** VMnet2 is used as an isolated switch. It is not defined in the Virtual Network Editor, so it has no VMware DHCP server and no host (Windows) adapter on it. This is intentional: the Windows host cannot reach the lab directly and there is no address conflict with gw01's 192.168.60.1.

## 3. Procedure

### 3.1 Identify interfaces and the netplan file

```bash
ip -br a
ls /etc/netplan/
```

- ens33 = first adapter (NAT), ens34 = second adapter (VMnet2) on all three VMs.
- The Ubuntu installer created `/etc/netplan/50-cloud-init.yaml` (not `00-installer-config.yaml` as assumed in the guide).

### 3.2 Stop cloud-init from overwriting the network config

`50-cloud-init.yaml` is generated by cloud-init and can be regenerated at boot. Network management by cloud-init was disabled so the manual configuration persists:

```bash
echo "network: {config: disabled}" | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
cat /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
```

### 3.3 gw01 – gateway configuration

```yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: true
    ens34:
      addresses: [192.168.60.1/24]
```

ens33 keeps DHCP (and therefore the default route to the internet); ens34 has no gateway because gw01 *is* the gateway.

### 3.4 app01 / stor01 – internal servers

```yaml
network:
  version: 2
  ethernets:
    ens34:
      addresses: [192.168.60.10/24]   # stor01: 192.168.60.20/24
      routes:
        - to: default
          via: 192.168.60.1
      nameservers:
        addresses: [1.1.1.1, 8.8.8.8]
```

### 3.5 Apply safely

```bash
sudo chmod 600 /etc/netplan/50-cloud-init.yaml
sudo netplan try      # auto-rollback after 120 s unless confirmed
sudo reboot           # prove the configuration survives a restart
```

`netplan try` was used instead of `netplan apply` because it rolls back automatically if the change breaks connectivity – the safe habit for remote servers.

## 5. Issues encountered

| # | Symptom | Cause | Resolution |
|---|---|---|---|
| 1 | Netplan file from the guide did not exist | Ubuntu 22.04 installer names it `50-cloud-init.yaml` | Edited the existing file; disabled cloud-init network management so it is not regenerated |
| 2 | YAML pasted into the VMware console arrived garbled (wrong characters, staircase indentation) | VM keyboard layout differs from the host layout, and vim auto-indents pasted text | Left vim without saving (`Esc`, `:q!`) and typed the file by hand in nano using spaces |
| 3 | `netplan` warned that the file permissions are too open | File was world-readable | `sudo chmod 600 /etc/netplan/50-cloud-init.yaml` |
| 4 | `netplan try` printed an Open vSwitch warning | netplan checks for Open vSwitch, which is not installed | Harmless, ignored – no OVS interfaces are used |
| 5 | app01 still had a 192.168.229.x address on ens33 | NAT adapter was still connected in VM settings | Unticked *Connected* and *Connect at power on* for the NAT adapter, rebooted; ens33 now DOWN |
| 6 | VMnet2 not visible in the Virtual Network Editor | It is an isolated custom switch, not a host-only network | Confirmed as correct for the design (see section 2) |
| 7 | `lsblk` on stor01 shows only `sda`; the two 5 GB data disks planned for LVM are missing | Disks were planned but never added to the VM | Powered off, added 2 × 5 GB SCSI disks in VM settings; `lsblk` now shows `sdb` and `sdc` |

## 6. Lessons learned

- Check which file the system actually uses (`ls /etc/netplan/`) instead of assuming a name from documentation.
- cloud-init can silently override manual network changes; disabling its network module makes the configuration owned by the admin.
- `netplan try` + a reboot test is the safe way to change networking: rollback if wrong, proof of persistence if right.
- Network isolation is enforced at the **hypervisor** level (disconnected adapter), not just in the OS – an internal server should not have an internet adapter at all.
- Verify hardware against the plan (`lsblk`) early – a missing disk found now costs one minute, found in Phase 2 it blocks the whole storage phase.
- Pasting through a VM console is unreliable across keyboard layouts; typing short config files by hand is faster than debugging garbled input.
