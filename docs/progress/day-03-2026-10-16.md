## 1. The story – why a service desk, and why now

💡 **In plain words:** until now I fixed problems and wrote them down in these reports. A real IT team does not work like that: every problem, every change and every "please give me access" goes into a **ticket system**, so anyone can see *what happened, who fixed it, how, and when*. Phase 1A gives Acme that system.

**Where it fits in the Acme story.** The brief says: *"nobody can say who changed what"* and *"the first enterprise customer's security questionnaire asks questions the team cannot answer."* The network (Phase 1) now works, so this is the right moment: from Phase 2 on, **every incident I cause and fix becomes a real ticket**, every planned change (e.g. "grow /data by 1 GB") becomes a **change** ticket with a rollback plan, and every server appears in an **asset inventory** automatically.

| Ticket type | Meaning | Example in this project |
|---|---|---|
| **Incident** | Something broke | "stor01 read-only file system" (happened on Day 1) |
| **Change** | A planned change with a plan and a rollback | "Grow /data by 1 GB", "Enable UFW on stor01" |
| **Request** | Someone asks for a routine thing | "Give alice access to app01", a password reset |
| **Knowledge base (KB)** | The written fix, so the next person solves it faster | "Always run `mount -a` before a reboot" |
| **Asset inventory** | Every server with CPU, RAM, disks, IPs and installed software | gw01, app01, stor01, svc01 |

📊 **The picture – how a service desk works:**

![How a service desk works – GLPI on svc01](../images/service-desk-overview.png)

**Key understanding (in my own words).**

> In the IT industry a problem is an **incident**, and handling them is **incident management**. When someone asks for a routine thing – a new user, a password reset, access to a server – it is a **request**. When I modify a system itself – grow a disk, enable a firewall, upgrade software – it is a **change**, which needs a plan, approval and a way back. All three are **tickets** in GLPI, and every ticket moves through the same steps: new → assigned → in progress → solved → closed; a solved fix is written down in the **knowledge base**. The **asset inventory** is not a ticket: it is the list of every machine and what is on it, filled automatically by the GLPI agent on each server, so a ticket can say which server it is about. GLPI follows **ITIL**, the common rule book for running IT services, and is used by many European companies and public bodies.

**Who can reach svc01?** svc01 has **no public IP** – it sits on the private lab network behind gw01, like app01. Staff and admins reach it from inside the company network (in the lab: my PC through VMware's host adapter; from Phase 6A through the WireGuard VPN). **Customers never reach it directly**: they email or call support, and support opens the ticket for them. A service desk holds the details of every server, so exposing it to the internet would be a security risk.

**Why svc01 appears twice in the picture:** in the middle it is the **GLPI application** (the help desk); on the right it is the **machine** svc01, which also runs a GLPI agent and lists itself in the inventory. GLPI itself runs only on svc01; the other servers get only the small agent.

**Incident or change?** "The server is broken, please update it" is an **incident** (something is broken). "The server runs an old version, upgrade it next Tuesday" is a **change** (planned). The SLA – how fast a ticket must be handled – is the IT team's promise, not something the customer sets.

**Why GLPI.** GLPI is a free, ITIL-style service desk used by many European companies and public bodies. Freshservice or ServiceNow need a paid licence; GLPI teaches the same concepts – incident, change, request, SLA, KB, CMDB – and they carry over to any tool.

**Why it matters for my job search.** Many of the junior IT / DevOps postings I reviewed ask for ticket systems, SLAs, asset management or knowledge articles. In an interview I can say: *"I ran my lab through GLPI. Every incident I caused has a ticket, a root cause and a KB article, and every server is in the inventory."*

**Why a separate server.** The service desk must keep working when the servers it tracks are broken – if app01 is down, I still need to open the incident ticket. So it gets its own VM, `svc01`. Later, Project 1 reuses the same svc01 as a second "customer" – one service desk serving two customers is how IT system houses and managed service providers work.

## 2b. Three examples, start to finish

**How the GLPI agent fits in:** a small program on each server looks at its own machine once a day (CPU, RAM, disks, IP, software) and sends the report to `http://svc01` – finding svc01 through `/etc/hosts` or DNS. GLPI stores it as an **asset**. The agent creates no tickets and nobody logs in through it. Tickets come from **people**; in each ticket the person picks the affected server ("Item: app01") from the inventory, which links the ticket to the machine.

| Thing | Question it answers | Used by |
|---|---|---|
| `/etc/hosts` / DNS | "What is stor01's IP?" | Machines, to connect |
| Asset inventory | "What is app01, what does it have?" | People, to know and plan |
| Ticket | "What is wrong or needed, and who did what?" | People, to work |

1. **Alice (employee) → Incident.** "I can't open the shared folder on app01." Item: app01. L1 checks (app01 pings, folder hangs) → escalates to **Linux Admins (L2)** with notes → L2 finds the firewall blocking NFS on stor01, fixes it, writes the root cause → Solved → KB article → alice confirms → Closed.
2. **Team lead → Request.** "New developer carol starts tomorrow; account on app01 in group devs." L1 runs `useradd -m -s /bin/bash -G devs carol` and `passwd carol` → Solved → Closed. When carol leaves: a new request → `usermod -L carol`.
3. **Admin → Change.** "/data on stor01 is 90 % full." The inventory shows 4 GB free in the storage pool → change ticket "Grow /data by 1 GB" with plan (`lvextend -r -L +1G`), risk, rollback (LVM snapshot first) and approval → done → `df -h` checked → Closed. The next agent run shows the new size automatically.

**In the lab I play every role** with separate GLPI accounts: `alice`/`bob` as requesters, `tech.bilal` in the groups **Service Desk (L1)** and **Linux Admins (L2)**. Escalation = reassigning the ticket to the higher group with notes; the history stays with the ticket.

## 4. Installation and first boot

### 4.1 No network after the install

📸 **Evidence – two cards, both DOWN, no IP address; only one netplan file:**

![ens33 and ens34 down](../images/day-03/03-svc01-two-cards-down-no-ip.png)

| | |
|---|---|
| **Seen** | `ip -br a` shows `ens33` and `ens34`, both **DOWN** and without an address; `ip route` is empty; `ping` says *Network is unreachable*. |
| **Cause** | The NAT adapter was still attached during the install (two cards), and the manual network settings from the installer were not applied. |
| **Fix** | Stop cloud-init from managing the network (as on app01 and stor01, Day 1) and write the netplan file for `ens34` (the VMnet2 card) by hand. |

```bash
echo "network: {config: disabled}" | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
sudo tee /etc/netplan/50-cloud-init.yaml > /dev/null << 'EOF'
network:
  version: 2
  ethernets:
    ens34:
      dhcp4: false
      addresses: [192.168.60.40/24]
      routes:
        - to: default
          via: 192.168.60.1
      nameservers:
        addresses: [8.8.8.8, 1.1.1.1]
EOF
sudo chmod 600 /etc/netplan/50-cloud-init.yaml   # only root may read it
sudo netplan try                                 # applies it; reverts after 120 s unless I press Enter
```

## 5. Growing the disk before Docker (LVM) – 2026-10-17

💡 **In plain words:** the welcome screen showed the system using only **11.5 GB of the 25 GB disk**. GLPI is about to move in – Docker images, a MySQL database with every ticket, user and inventory record, and ticket attachments – and all of it grows every day. A full disk makes MySQL crash, which would take the service desk itself down: exactly the Acme problem *"disks fill up without warning"*. So the disk was grown **before** installing anything. The system was also fully patched first, because GLPI will open a web service on port 80.

```bash
ip -br a                                                # ens34 192.168.60.40 (ens33 = old NAT adapter, to be removed)
sudo vgs                                                # the pool: VSize 23 GB, VFree 11.5 GB unused
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv  # give the volume all free space; -r grows the file system too
df -h /                                                 # 23 GB, 28 % used
sudo apt update && sudo apt upgrade -y                  # patch before opening a service
```

![vgs, lvextend, df](../images/day-03/16-svc01-vgs-lvextend-df.png)

📸 **Evidence – all packages up to date:**

### Reading `vgs`

| Column | Value | Meaning |
|---|---|---|
| VG | `ubuntu-vg` | Name of the pool |
| #PV | 1 | Built from 1 physical volume |
| #LV | 1 | 1 logical volume cut from it |
| #SN | 0 | No snapshots |
| VSize / VFree | 23 GB / 11.5 GB | Pool size / part not given to any volume yet |

### The picture – boxes inside boxes

![svc01 storage layers](../images/day-03/14-svc01-storage-layers.png)

| Part of the command | Meaning |
|---|---|
| `lvextend` | Make a logical volume bigger |
| `-l +100%FREE` | Small **l**: add all free space of the pool (capital `-L +5G` would add an exact size) |
| `-r` | Resize the **file system** too – otherwise the volume grows but the space is not usable |
| `/dev/ubuntu-vg/ubuntu-lv` | Path pattern `/dev/<VG>/<LV>` |

### Docker: image, container, mounted folder

| Word | Simple meaning | Here |
|---|---|---|
| **Image** | The installer – a ready-made program package that never changes | `glpi/glpi`, `mysql:8.0` (kept in `/var/lib/docker`) |
| **Container** | The running program made from the image | GLPI and MySQL running |
| **Mounted folder (volume)** | A real svc01 folder shown inside the container, where it saves its data | `/opt/helpdesk/storage/mysql` → `/var/lib/mysql` inside MySQL |

A container is thrown away when it is updated or recreated; data saved in the mounted folder on svc01 survives.

### Same layers in Windows

![Linux LVM vs Windows Storage Spaces](../images/day-03/15-linux-lvm-vs-windows-storage.png)

📸 **On my own PC (Disk Management, `diskmgmt.msc`): a "Basic" disk – Disk 0 cut into partitions with drive letters (C:, D:), no pool layer:**

![Windows Disk Management](../images/day-03/18-windows-disk-management-basic-disk.png)

Where to look in Windows: **Disk Management** (Win + X) for disks, partitions and letters; **Storage Spaces** (Control Panel, or Server Manager → File and Storage Services → Storage Pools on Windows Server) for pools; PowerShell `Get-Disk`, `Get-Partition`, `Get-Volume`, `Get-StoragePool`.

### Key understanding (in my own words)

> When I created svc01, I gave it one 25 GB virtual disk, **sda**. A disk can be divided into **partitions**, like C: and D: in Windows. Here, sda1 and sda2 are for booting, and **sda3** (23 GB) is used as a **physical volume (PV)**. On its own, a PV is just raw space. It is never divided: once it is added to a **volume group (VG)**, a pool of space, it belongs to that VG only. One VG can be built from one or several PVs. Here there is one VG, `ubuntu-vg` (23 GB), made from one PV. For a second VG, I would first create another partition on the disk, which becomes its own PV.
>
> Inside a VG I can create many **logical volumes (LVs)**. Here there was one, `ubuntu-lv`, with 11.5 GB, and the other 11.5 GB were free. I could have used the free space for more LVs; separate LVs give **isolation of space**: if one fills up (for example `/var/log` with logs), the others are not affected, and each LV can be grown, backed up or snapshotted on its own. This is about disk space, not security; data is protected by permissions, firewalls and encryption. On svc01 I chose to grow the single LV to the full 23 GB with `lvextend -r -l +100%FREE` while the system was running, and `-r` grew the file system too.
>
> An LV is only usable once it is **formatted** (ext4) and **mounted**; this one is mounted as `/`, the umbrella for every folder (`/etc`, `/home`, `/var/log`, `/var/lib/docker`, `/opt`).
>
> The same idea in Windows: physical disks (≈ PVs) are added to a **Storage Pool** (≈ VG) in Storage Spaces. The pool is cut into **virtual disks** (≈ LVs), which are formatted with NTFS or ReFS (≈ ext4) and given a drive letter such as D: (≈ mounting). Extend Volume in Disk Management grows a volume live, like `lvextend -r`. Linux uses one folder tree under `/`, while Windows uses drive letters, but the layers are the same: disk → pool → volume → file system → mount point. On a normal PC like mine the disk is "Basic": only partitions with drive letters, no pool – storage pools are used on servers with several disks.
>
> For the service desk, Docker takes **images** (the installers for GLPI and MySQL) and runs them as **containers**. Their data is saved in **mounted folders** on svc01, for example `/opt/helpdesk/storage/mysql`, which appears inside MySQL as `/var/lib/mysql`. So tickets, users and inventory stay safe on `/` even if a container is deleted or upgraded, and that is why I grew the disk before installing GLPI.

## 6. The network story – from the first picture to today

💡 **Read this section alone and you have the whole network in your head – no need to go back to Day 1.**

**Picture 1 – the plan.** Acme gets four servers on one private lab network, and one gatekeeper (gw01) between that network and the internet.

![Project architecture](../project2-architecture.png)

**Picture 2 – the gatekeeper (Phase 1).** In the beginning every VM had its own NAT card straight to the internet. That is easy but unsafe: nobody controls the traffic. So the servers' outside cards were removed. Only **gw01** keeps two cards: **ens33** towards VMware's **VMnet8** (the way out) and **ens34** = `192.168.60.1` on **VMnet2** (the lab). With IP forwarding and an iptables MASQUERADE rule, gw01 became a router with NAT – the same job a cloud NAT gateway does.

![Linux NAT vs cloud NAT](../images/nat-linux-vs-cloud.png)

**Picture 3 – two virtual switches.** VMware builds switches in software. **VMnet2** is the lab switch: app01, stor01, svc01 and gw01's inside card are plugged into it, so they talk to each other **directly** (no router, no NAT – `ttl=64`); `/etc/hosts` only turns their names into IPs. **VMnet8** is the way out: only gw01's outside card is plugged into it. A *host adapter* is a cable from my Windows PC into one switch – it already had one into VMnet8, but **none into VMnet2**.

![Two switches and the host adapters](../images/day-03/20-two-switches-host-adapters.png)

**Picture 4 – three paths.**
① **Inside:** server ↔ server over VMnet2, directly.
② **Out:** a server → gw01 (**NAT 1**, to gw01's VMnet8 address) → VMware NAT (**NAT 2**, to my Wi-Fi card's address) → home router (**NAT 3**, to my public IP) → internet. DNS (8.8.8.8) is on the internet too, so name lookups for google.com take the same path – that is why nothing worked while gw01 was off.
③ **In:** my browser → svc01. This needs my PC on the lab switch, so the **VMnet2 host adapter** is added with the free address `192.168.60.250` (not .1 – that is gw01). It is a local side door for this one PC, not a VPN; in **Phase 6A** it is replaced by a WireGuard VPN through gw01 – the way a real remote worker comes in.

![Three paths in the lab](../images/day-03/19-three-paths-in-the-lab.png)

**Why today:** GLPI now runs on svc01 and answers `200 OK` from svc01 itself and from gw01. To use the service desk in a browser, my PC needs path ③.

**How names are found (two places, in order – `hosts: files dns` in `/etc/nsswitch.conf`):**

| Order | Where Linux looks | Lab names (stor01) | Internet names (google.com) |
|---|---|---|---|
| 1 | `/etc/hosts` (local list) | ✅ found here | ❌ not there |
| 2 | DNS via the helper 127.0.0.53 → 8.8.8.8 | ❌ no DNS server knows the lab | ✅ found here (and cached) |

**Switch, router, bridge:**

| Device | Like | In the lab |
|---|---|---|
| Switch | an extension board – devices on the same network plug in and talk directly | VMnet2 (lab board), VMnet8 (way-out board) |
| Router | a person between two boards passing messages across | gw01 – one card on each board |
| Bridge (VMware "Bridged") | plugging a VM straight into the home network | not used – the lab stays separate |

Network adapter (VMware) = `ens34` / `ens33` (Linux) = network card (NIC) – one thing, three names.

> **Key understanding (in my own words).**
> Every server has a network card. VMware calls it a "Network Adapter". Inside Linux the card is called `ens34` or `ens33`.
>
> A virtual switch is like an extension board. VMnet2 is the lab board. VMnet8 is the board for the way out.
>
> app01, stor01 and svc01 are plugged into VMnet2. gw01 is also plugged into VMnet2 with its inside card. All of them have an address in the same network. So they talk to each other directly by IP. This worked from the first day.
>
> To use names, Linux looks in two places. First it checks `/etc/hosts`. Then it asks DNS. Our lab names are written in `/etc/hosts`, so they are found in the first place. Internet names like google.com are not in `/etc/hosts`. So Linux asks DNS. The helper 127.0.0.53 forwards the question to 8.8.8.8 and keeps the answer in a cache.
>
> For the internet, the servers send their traffic to gw01. gw01 has a second card on VMnet8. The address is changed three times on the way out. First gw01 changes it to its own address on VMnet8. Then VMware's NAT changes it to my Wi-Fi card's address. Then my home router changes it to my public IP. The DNS question to 8.8.8.8 also takes this way. So nothing on the internet works while gw01 is off.
>
> My Windows PC had a card on VMnet8 but no card on VMnet2. So my browser could not reach svc01. Now I give my PC a card on VMnet2 with the tick "Connect a host virtual adapter". The card gets the address 192.168.60.250. My browser can now open GLPI on svc01 directly. Nothing changes for the servers.

## 8. Step 1A.4 – GLPI agent: automatic asset inventory – 2026-10-17

💡 **In plain words:** a small program, the **GLPI agent**, now runs on every server. Once a day it collects what the machine is made of – hardware, operating system, serial number, installed software, network cards – and sends it to GLPI on svc01. So the asset list fills itself and stays up to date; nobody types it in. The agent is not a person and creates no tickets. (The guide puts Step 1A.4 after 1A.3; I did the inventory first because it only needs GLPI running.)

### 8.1 Switch the inventory on in GLPI

| Risk | Any machine on the network could send a fake inventory | Acceptable inside the lab |
