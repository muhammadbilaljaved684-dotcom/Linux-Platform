## 1. Objective

💡 **In plain words:** before a mechanic repairs a car, they write down its condition: mileage, oil level, warning lights. Then, if something goes wrong later, they can compare against "how it was before". This phase does the same for a server: **write down how it looks before I change anything.**

🔧 **Technical:** record a **baseline** of the gateway server gw01: kernel version, loaded drivers, memory, IP forwarding state, boot time and boot target. The baseline is the reference point for every later change, for troubleshooting ("what was it like before?") and for audits.

## 3. Step 0.1 – Kernel, drivers and memory

💡 **In plain words:** the **kernel** is the "engine" of Linux – the core program that talks to the hardware. **Drivers (modules)** are small add-ons that let the engine use specific hardware. Here I check *which engine version* the server runs, *which add-ons are loaded* and *how much memory it has*. I also check one important switch: whether this machine is allowed to pass traffic between networks (like a router) – right now it is not.

🔧 **Commands (run on gw01):**

```bash
uname -r                      # print only the kernel version
uname -a                      # print everything: hostname, kernel, build date, CPU architecture
cat /proc/version             # the kernel's own description: compiler and build details
lsmod | head                  # list loaded kernel modules (drivers); "| head" shows only the first 10 lines
free -h                       # memory and swap usage, "-h" = human-readable (GiB/MiB)
sysctl net.ipv4.ip_forward    # read the kernel setting that decides whether this host routes packets
```

![Kernel, modules, memory and ip_forward on gw01](../images/day-01/01-phase0-kernel-memory.png)

| Check | Result | What it means |
|---|---|---|
| Kernel version | `5.15.0-198-generic` | Ubuntu 22.04 standard kernel; noted so future updates can be tracked |
| Build info | gcc 11.4.0, binutils 2.38 | Standard Ubuntu build, nothing custom |
| Loaded modules | `vmw_vsock_*`, `vmw_balloon`, `vsock`, `intel_rapl_*` | VMware guest drivers are loaded – the OS knows it runs as a VM. `vmw_balloon` lets VMware take back unused memory |

## 4. Step 0.2 – Boot process

💡 **In plain words:** starting a computer is a relay race – each runner hands over to the next: the **firmware** wakes the hardware → the **bootloader (GRUB)** picks and loads the engine → the **kernel** starts → **systemd**, the "manager", starts all the services (network, SSH, …) → you get a login. Here I measure **how long the race takes** and save the details as evidence.

🔧 **Commands (run on gw01):**

```bash
systemd-analyze                               # total boot time, split into kernel and userspace
systemd-analyze blame >> boot-gw01.txt        # time per service, appended (>>) to a file as evidence
journalctl -b | head -15 >> journal-gw01.txt  # first 15 log lines of this boot (-b), appended to a file
ls /boot                                      # files the bootloader uses to start Linux
```

📸 **Evidence:**

![systemd-analyze and /boot contents on gw01](../images/day-01/02-phase0-boot-analysis.png)

| Check | Result |
|---|---|
| Total boot time | **38.117 s** = 17.022 s kernel + 21.095 s userspace (services) |
| Default target reached | `graphical.target` after 19.809 s in userspace |
| `/boot` contents | `vmlinuz-5.15.0-198-generic` (the kernel), `initrd.img-5.15.0-198-generic` (initial RAM disk – a mini system that helps the kernel find the real disk), `vmlinuz.old` / `initrd.img.old` (**previous kernel kept as a fallback** if an update fails), `grub/` (bootloader), `config-*` and `System.map-*` (kernel build settings and symbol map) |

**Boot chain:** firmware (BIOS/UEFI) → GRUB bootloader → Linux kernel → initramfs → systemd (PID 1) → services → login.

## 5. Step 0.3 – Boot target (desktop mode vs server mode)

💡 **In plain words:** Linux can start in different "modes", called **targets**. `graphical.target` starts a desktop with windows and mouse – useful for a laptop, wasted on a server nobody sits in front of. `multi-user.target` starts everything a server needs (network, services, logins) **without** the desktop. Less software running = faster start, less memory used and fewer things an attacker could abuse.

🔧 **Commands (run on gw01):**

```bash
systemctl get-default                            # which target the system boots into now
sudo systemctl set-default multi-user.target     # change it to server mode (needs admin rights: sudo)
systemctl get-default                            # check that the change took effect
```

📸 **Evidence** (including my first typo, see issues):

![Changing the default boot target on gw01](../images/day-01/03-phase0-boot-target.png)

| Before | After |
|---|---|
| `graphical.target` | `multi-user.target` |

systemd confirmed the change by creating the link `/etc/systemd/system/default.target → /lib/systemd/system/multi-user.target`.

| Old "runlevel" (classic Linux) | systemd target today |
|---|---|
| 0 | poweroff.target |
| 1 | rescue.target (repair mode) |
| 3 | multi-user.target (server) |
| 5 | graphical.target (desktop) |
| 6 | reboot.target |

## 6. Issues encountered

| # | Symptom | Cause | Resolution |
|---|---|---|---|
| 1 | `systemctl get default` → `Unknown command verb get.` | Typo: the command is `get-default`, one word with a hyphen | Re-ran as `systemctl get-default` |
| 2 | Unsure whether `>> tee file` saves output | `>>` sends output to a **file**; `\|` (pipe) sends it to a **program**. `>> tee` would create a file literally named `tee` | Use `command \| tee file` (show on screen **and** save) or `command >> file` (append to file only) |

## 7. Lessons learned

- A baseline captured **before** changes makes later troubleshooting faster and provable.
- `ip_forward` is the single kernel setting that decides whether a Linux host routes traffic.
- Servers should boot into `multi-user.target`; the previous kernel in `/boot` is the safety net if an update fails.
- Saving command output to files turns "I did it" into evidence for documentation and audits.
